# KARUNA AJN medical trust — Phase 1

A Next.js foundation for KARUNA AJN medical trust in India. Includes a public website, protected staff dashboard, Supabase authentication, and a private relational schema. **No clinical workflow is enabled.** No real patient information is included.

## Start locally

Use Node.js 22.13+ (Node 24 LTS recommended) and npm.

```sh
npm ci
cp .env.example .env.local
npm run dev
```

On PowerShell, replace the copy command with `Copy-Item .env.example .env.local`.
Open http://localhost:3000. Without environment values, the public website works and login shows a setup notice. Dashboard access remains blocked; there is no authentication bypass or public dashboard demo route.

## Configure Supabase

1. Create a dedicated Supabase development project. Choose its region according to the trust’s documented data-handling requirements.
2. In the project Connect dialog, copy the project URL and **publishable** key into `.env.local`:
   - `NEXT_PUBLIC_SUPABASE_URL`
   - `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`
   - For a legacy project, `NEXT_PUBLIC_SUPABASE_ANON_KEY` may replace the publishable key.
3. Leave `SUPABASE_SERVICE_ROLE_KEY` blank. Phase 1 does not use it. Never use a secret/service-role key in a `NEXT_PUBLIC_*` variable.
4. Install the official Supabase CLI, authenticate, and link the project:

```sh
supabase login
supabase link --project-ref YOUR_PROJECT_REF
supabase db push
```

Run commands from this project folder. Review the target project before pushing. The migrations are intended for a new project:

- `supabase/migrations/202610010001_foundation.sql`: tables, constraints, IDs, roles, indexes, timestamps, audit triggers, grants and RLS.
- `supabase/migrations/202610010002_storage.sql`: two private buckets; no upload/download policies.

For a local Supabase environment with Docker: `supabase start`, then `supabase db reset`. Reset deletes the local database; do not use it against a populated shared environment. Seed data is disabled. Database tests create isolated, fictional fixtures only.

## Provision the first staff member

Phase 1 deliberately has no public signup, administrator bootstrap URL, or service-role endpoint.

1. In Supabase Authentication settings, disable new user signups and anonymous sign-ins. Local configuration already disables signup; hosted project settings must be configured separately.
2. Use the Supabase dashboard’s **Add user / Create user** option to create a confirmed email/password account for a known staff member. Invitation and password-recovery callback routes are not included in Phase 1. Do not use an invitation flow that assumes this application handles email links.
3. Copy the new Auth user UUID. Use a trusted SQL session in the project to create the trust, profile and active membership. Replace every placeholder before running:

```sql
begin;
insert into public.trusts (id, name)
values ('REPLACE_WITH_TRUST_UUID', 'REPLACE_WITH_OFFICIAL_TRUST_NAME');
insert into public.profiles (id, display_name)
values ('REPLACE_WITH_AUTH_USER_UUID', 'REPLACE_WITH_STAFF_DISPLAY_NAME');
insert into public.trust_memberships (trust_id, user_id, active)
values ('REPLACE_WITH_TRUST_UUID', 'REPLACE_WITH_AUTH_USER_UUID', true);
insert into public.user_roles (trust_id, user_id, role_id)
values ('REPLACE_WITH_TRUST_UUID', 'REPLACE_WITH_AUTH_USER_UUID', 'trust_admin');
commit;
```

Use UUIDs generated by a trusted tool, for example PostgreSQL `select gen_random_uuid();` for the trust. Reuse an existing trust ID for later staff; do not create duplicate trusts. No profile or membership is created from user-controlled signup metadata. Role assignment is preparatory and **does not grant clinical access** in Phase 1.

4. Configure Auth Site URL for the local or Vercel domain. Keep redirect URLs limited to known development/production URLs. Configure provider password policies and Auth rate limits in Supabase.
5. Restart the app after changing environment variables. Sign in at `/login`, verify `/dashboard`, and verify sign-out. Deactivate a membership and confirm access is denied on the next server request.

## Database types

`src/types/database.ts` is explicitly a handwritten, read-only subset for the only two tables queried in Phase 1. After applying the schema, replace it with generated definitions:

```sh
supabase gen types typescript --linked --schema public > src/types/database.ts
npm run typecheck
```

Use UTF-8 output when redirecting on Windows (PowerShell 7 recommended). Do not claim the supplied subset is generated from a live project.

## Quality checks

```sh
npm run typecheck
npm run lint
npm test
npm run test:database
npm run build
```

With the built app running via `npm start` and Supabase environment values unset, run `npm run test:routes` to verify public routes, private-route redirects, cache protection and 404 handling. Set `TEST_BASE_URL` if using another local port. This check intentionally does not log in or alter any account.

Database tests use PGlite, a local PostgreSQL engine, with minimal Auth/Storage schema stubs. They apply both migrations and test relationships, constraints, RLS, grants, private bucket metadata, and audit records. They do not prove hosted Supabase Auth, Storage, network behavior, email delivery, backup configuration, or Vercel deployment. Perform the live checks in `docs/SECURITY.md` before handling real records.

In restricted Windows environments that block child-process spawning, run the build with `$env:NEXT_BUILD_WORKER_THREADS='1'` first. This opt-in uses Next.js worker threads and its TypeScript API checker; it does not skip type checking. Standard local/Vercel builds use Next.js defaults. Dependencies were installed here with lifecycle scripts disabled because of that environment restriction; compilation and all included checks were still run successfully.

## Vercel

Import this directory as a Next.js project, use a supported Node version, and configure the two required public Supabase environment variables separately for development, preview and production. Use a separate Supabase development project for previews. Build command: `npm run build`; start is managed by Vercel. No Vercel-specific dependency is required. Update Supabase Auth URLs to the approved deployed domain. No deployment has been performed as part of this handover.

Keep the site private until official branding, contact information, accessibility review and security setup are complete. `robots` metadata currently requests no indexing; this is not access control. Remove it intentionally at public launch. The public site currently exposes no database content.

## Project structure

```text
src/app/                    App Router layouts, pages, loading/error boundaries
src/components/             Shared UI, native dialog, public/staff navigation
src/features/auth/          Login form and server actions
src/features/dashboard/     Isolated fictional presentation fixtures
src/features/public/        Public placeholder page copy
src/lib/supabase/           Browser/server clients
src/lib/env.ts              Public configuration validation
src/services/               Server-only staff access checks
src/schemas/                Shared Zod input contracts
src/types/                  Explicitly scoped database types
src/proxy.ts                Verified session refresh and route gate
supabase/migrations/        Reproducible database foundation
tests/                      Validation and PostgreSQL security tests
docs/                       Architecture and security handover
```

UI files do not query the database. Future business operations should live in server-only services, called from validated actions or route handlers. Each future operation must independently verify membership and permission; a protected layout alone is insufficient. Add analytics services only when real reporting is implemented. Recharts and import libraries are intentionally not installed yet.

## Routes

Public: `/`, `/about` (combined trust story, care approach and privacy-safe impact plan), `/camps`, `/camps/[id]`, `/gallery`, `/contact`, `/login`.
The former `/services` and `/impact` pages are removed; their content now lives on `/about`.
No camps are published, so all camp detail IDs return 404. Unknown public slugs also return 404.

Protected: `/dashboard`, `/dashboard/camps`, `/dashboard/patients`, `/dashboard/referrals`, `/dashboard/follow-ups`, `/dashboard/reports`, `/dashboard/gallery`, `/dashboard/users`, `/dashboard/settings`.
The overview contains explicitly fictional totals and camp rows. All other staff modules are placeholders.

## End-of-phase status

- Files: see this structure and `docs/ARCHITECTURE.md`; the entire deliverable is this folder plus its lockfile.
- Tables: 21 application tables, one private counter table, and Supabase-managed `auth.users`. Full list in architecture notes.
- Authentication: email/password, session refresh, active membership verification, protected dashboard, local-session logout implemented. Live verification requires your project and staff account.
- Security: clinical tables closed to application roles; RLS on all application tables; no public clinical views or APIs; immutable-to-staff audit log; composite trust foreign keys; no service-role usage; validated input; private buckets; generic user errors; server-only access service.
- Deferred: complete RBAC, patient/camp CRUD, clinical workflows, imports, reporting, notifications, uploads, publication, analytics, account invitations/recovery, and production operational hardening.
- Manual setup: Supabase project, environment values, migrations, initial staff provisioning, hosted Auth settings, live checks, optional Vercel deployment, official branding/content.
- Known limitations: see `docs/SECURITY.md`. Phase 1 is a foundation, not a certified or launch-ready health-record system.

Stop at Phase 1. Phase 2 requires a separate scope and review.
